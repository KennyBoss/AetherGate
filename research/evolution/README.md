# Запуски эволюции и гипотез

Установка из корня проекта (Python 3.12 или 3.13; Hydra 1.3 несовместима с 3.14):

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements.lock
.venv/bin/python run_evolution.py
.venv/bin/python run_evolution.py experiment=formulas
.venv/bin/python run_evolution.py experiment=selfplay experiment.parameters.seed=17
```

Параметры находятся в `configs/evolution/experiment/`. Hydra объединяет выбранный
эксперимент с общей конфигурацией; значения можно переопределять в командной
строке. Например, `experiment.parameters.proposals=/path/to/proposals.jsonl`.
Текущая рабочая папка сохраняется, поэтому относительные пути считаются от неё.
Результаты, обратная связь и `.hydra/` с настройками запуска сохраняются в
отдельной папке `artifacts/evolution/`. Для просмотра настроек без вычислений:
`run_evolution.py --cfg job`. Старые команды запуска скриптов продолжают работать.

Входные JSON-массивы и JSONL используют строгие модели Pydantic. Все четыре
операции формулы обязательны; допустимы только операции DSL, неизвестные поля
и неверные типы отклоняются. Метаданные `id`, `name`, `source`, `rationale`
необязательны и должны быть строками. Старый плоский формат формулы поддерживается.
Канонический формат:

```json
{"id":"probe","rationale":"Проверка базовой формулы","formula":{"memory_op":"identity","input_op":"identity","combine_op":"add","final_op":"tanh"}}
```

Формальная JSON Schema включена в `prompt.json`, передаваемый генератору.
Структурно повреждённый файл прекращает запуск; отдельная некорректная гипотеза
попадает в обратную связь как `rejected` и не передаётся на оценку.

Проверки из корня проекта:

```sh
make test-production PYTHON=.venv/bin/python
make ci PYTHON=.venv/bin/python
```

GitHub Actions запускает эти проверки на CPU при каждом pull request.
Для параллельной локальной проверки задайте отдельную папку результатов:
`VERIFY_ARTIFACT_DIR=artifacts/verify-local make ci PYTHON=.venv/bin/python`.
При прямом запуске `run_evolution.py` изоляции контейнером нет:
команда `generator_command` выполняется на хосте. Для изоляции используйте Docker,
как описано ниже.
Конфигурации и seed не гарантируют побитовую воспроизводимость на другом железе.
Распределённые вычисления, удалённое хранилище и мониторинг требуют отдельных изменений.

## Изолированный запуск в Docker

Нужен работающий Docker Engine. Из корня проекта:

```sh
make docker-build
python3 run_evolution_docker.py --experiment hypothesis
python3 run_evolution_docker.py --experiment formulas experiment.parameters.seed=17
python3 run_evolution_docker.py --experiment selfplay experiment.parameters.generations=2
python3 run_evolution_docker.py --proposals /path/to/proposals.jsonl
```

Образ CPU используется локально и не публикуется в реестр. В контейнер копируются
только код эволюции, ядро, конфигурации и зависимости. Рабочая папка проекта,
Git, переменные окружения хоста, ключи и Docker socket внутрь не передаются.
Образ запускается непривилегированным пользователем, без сети и Linux capabilities,
с `no-new-privileges` и корневой файловой системой только для чтения.
Входной файл гипотез монтируется только для чтения. Команда генератора, если
задана через конфигурацию, также выполняется внутри этого офлайн-контейнера.

Каждый запуск получает новую папку `artifacts/evolution-docker/`; её можно выбрать
через `--output-dir` (папка должна ещё не существовать). В ней остаются JSON-результаты
и `.hydra/` с настройками. Лимиты: 2 CPU, 2 ГиБ RAM без swap, 256 процессов и
256 МиБ временной памяти. `--timeout` ограничивает длительность (по умолчанию
600 секунд); при завершении и тайм-ауте контейнер удаляется. Лаунчер запускайте
от обычного пользователя. Docker bind mount не поддерживает здесь запятые в пути.

```sh
make docker-test PYTHON=python3
```

CI собирает этот же образ, запускает все три режима с малым бюджетом и проверяет
ограничения внутри настоящего контейнера, после чего выполняет обычный системный
прогон. При локальном запуске тестов без `RUN_DOCKER_TESTS=1` выполняются только
проверки команды и обработки тайм-аута. Параметры изоляции описаны в
[документации Docker](https://docs.docker.com/reference/cli/docker/container/run/).

Контейнеры используют общее ядро с Docker Engine; это не отдельная виртуальная
машина. Для исполнения враждебного произвольного кода нужна более строгая граница,
например выделенный worker с gVisor или microVM. Этот образ поддерживает только CPU.


## Зафиксированные зависимости и воспроизводимость

`requirements.lock` фиксирует точные версии всех Python-зависимостей и SHA-256
дистрибутивов. CI и Docker устанавливают его с `--require-hashes`, затем запускают
`pip check`. `requirements.txt` остаётся входным списком требований.
Для пересоздания lock-файла нужен uv: `make lock`. Эта команда сохраняет уже
зафиксированные версии; для намеренного обновления добавьте `--upgrade` к команде
`uv pip compile` из Makefile и проверьте изменения lock-файла.

CI выполняет каждый из трёх режимов в двух отдельных контейнерах с seed=53,
одинаковыми настройками и входными гипотезами. Сравниваются все вычислительные
поля JSON: формулы, оценки, история, матрицы выигрышей и SHA-256 весов лучших
агентов и конечных популяций. Также сравниваются обратная связь и контекст
гипотез. Исключаются только измеренное время и производительность; NaN/Infinity
в вычислительных результатах приводят к ошибке теста. Третий запуск с seed=54
проверяет, что смена seed действительно меняет веса. Бюджет малый, но включает
отбор и мутации популяций.

Проверка относится к одному CPU-образу и фиксированным входным предложениям.
Она не гарантирует побитового совпадения на другом железе/GPU и не проверяет
повторяемость ответов внешнего LLM-генератора. Версии драйверов и базовый образ ОС
этим Python lock-файлом не фиксируются.


## Автоматическая остановка

Эволюция весов формул, оценка гипотез и обе популяции самоиграния проверяются
при инициализации и сразу после каждой мутации. NaN/Inf в любом весе или поле
метрик (включая прогрев, энтропию и матрицу выигрышей) останавливают весь запуск
до отбора или следующего вычисления. Проверяются также числовые настройки.

Разнообразие — среднеквадратичное стандартное отклонение по всем параметрам
генома между особями, а не только разброс наград или смещений действий.
При значении не выше `min_population_diversity` запуск останавливается;
порог по умолчанию `0.000001`, он должен быть конечным и положительным.
В самоигрании каждая роль проверяется отдельно. Для популяции из одной особи
проверка коллапса неприменима, но проверка NaN/Inf остаётся.
Порог можно изменить, например:

```sh
python3 run_evolution_docker.py --experiment selfplay experiment.parameters.min_population_diversity=0.00001
```

При штатном завершении `result.json` содержит `status: completed`. При срабатывании
защиты он содержит `status: stopped`, seed и `stop_reason`: код `nonfinite` или
`diversity_collapse`, этап, поколение, популяцию, имя повреждённого поля или
измеренное разнообразие и порог. Для эволюции сохраняются также индекс/поколение
архитектуры и формула. Некорректная конфигурация имеет код `invalid_configuration`
или `nonfinite` и этап `configuration`.
Процесс завершается с кодом 2, сообщение выводится в stderr. Диагностика сохраняется
по `output_json`; при прямом запуске без него — в `guardrail_stop.json` текущей
папки. В диагностике нет NaN/Infinity. Это отчёт об остановке, а не checkpoint
для возобновления; история незавершённого запуска в него не переносится.
Последний исправный checkpoint хранится отдельно, как описано ниже.

CI проверяет инъекции NaN и обоих знаков Inf в веса и метрики, а также блокировку
отбора/дальнейших поколений. В настоящем Docker для эволюции и самоиграния отдельно
проверяются клонирование единственного элитного агента без шума (коллапс) и
переполнение при большой конечной мутации (Inf); проверяется код выхода и
сохранённая причина. Обычные успешные и воспроизводимые запуски тоже остаются в CI.
Порог защищает от почти одинаковых весов; он не доказывает разнообразие поведения
агентов и может требовать настройки для другого масштаба весов.


## Checkpoint и возобновление

Для `formulas` и `selfplay` checkpoint включён автоматически: Hydra/Docker пишет
`checkpoint.npz` в папку запуска. В прямом CLI можно задать `--checkpoint-path`;
по умолчанию это `<output_json без расширения>.checkpoint.npz`, а без output JSON —
`formulas.checkpoint.npz` или `selfplay.checkpoint.npz` в текущей папке.

Checkpoint хранит текущие веса, ключ JAX PRNG, счётчики и историю. Для поиска формул
сохраняются также состояние Python RNG, популяция формул, результаты уже оценённых
архитектур и прогресс внутренней эволюции весов. Запись выполняется перед первым
вычислением и после каждого завершённого поколения/перехода поиска. Один файл
заменяется атомарно через временный файл, flush/fsync и rename; прерванная запись
не повреждает предыдущую копию. Используется NPZ с числовыми массивами и JSON,
загрузка pickle запрещена. Старые поколения checkpoint не накапливаются.

После прерывания создайте новую папку результатов и передайте предыдущий файл:

```sh
python3 run_evolution_docker.py --experiment formulas --output-dir artifacts/formulas-first
# Если запуск был прерван:
python3 run_evolution_docker.py --experiment formulas --resume-from artifacts/formulas-first/checkpoint.npz --output-dir artifacts/formulas-resumed

python3 run_evolution_docker.py --experiment selfplay --output-dir artifacts/selfplay-first
# Если запуск был прерван:
python3 run_evolution_docker.py --experiment selfplay --resume-from artifacts/selfplay-first/checkpoint.npz --output-dir artifacts/selfplay-resumed
```

Для Hydra без Docker используется `experiment.parameters.resume_from=/path/checkpoint.npz`,
для прямых скриптов — `--resume-from /path/checkpoint.npz`. Docker подключает входной
checkpoint только для чтения; новые снимки пишет в новую папку `/output`.
Указывайте те же параметры, включая seed и полный бюджет поколений. Они хранятся
в файле и проверяются: смена эксперимента, настроек, версий Python/JAX/NumPy или
исходного кода приводит к отказу загрузки. Разрешено менять пути результата,
нового checkpoint и входного checkpoint. Изменять общий бюджет при возобновлении
нельзя. Checkpoint не поддерживается для отдельного режима гипотез.

Продолжение начинается с последней сохранённой границы: незавершённое вычисление
может быть выполнено снова. SIGINT, SIGTERM и SIGKILL не требуют отдельной записи
в обработчике сигнала. Если сбой произошёл до первой успешной записи, checkpoint
ещё не существует. При остановке защитой сохраняется последний исправный снимок;
он не отключает защиту и при повторении проблемы запуск снова остановится.
Снимок завершённого эксперимента позволяет восстановить результат без повторной
оценки популяций. Это локальное хранение: гибель диска/хоста требует внешней копии.

CI в настоящем контейнере завершает процесс сигналом SIGKILL сразу после записи
поколения, запускает другой контейнер с этим checkpoint и сравнивает весь
вычислительный JSON с непрерывным запуском того же seed. Сравниваются история,
формулы, метрики, матрицы и SHA-256 весов; только время/производительность исключены.
Входной файл остаётся неизменным. Дополнительные тесты покрывают раннее и позднее
прерывание вложенного поиска, повреждённый файл, несовместимые настройки/окружение,
запрет pickle и сохранность предыдущего снимка при ошибке записи.
Гарантия совпадения относится к одинаковому CPU-окружению и оборудованию, а не к
переносу между разными CPU/GPU или версиями кода.


## S3-совместимое хранение артефактов

Установите зависимости из обновлённого `requirements.lock` и пересоберите образ
через `make docker-build`: он записывает Git HEAD в метку образа. Для точной
привязки к коммиту собирайте из чистого checkout. CI ставит метку из `GITHUB_SHA`.
Существующий bucket создаётся администратором отдельно; лаунчер его не создаёт.
Для доступа используется стандартная цепочка credentials boto3: AWS profile,
переменные `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN` или
роль окружения. Регион задаётся `AWS_DEFAULT_REGION`/профилем. Не помещайте ключи
в параметры эксперимента, Docker-образ или файлы результатов.

```sh
make docker-build
python3 run_evolution_docker.py --experiment formulas --output-dir artifacts/formulas-s3 --s3-uri s3://my-bucket/aethergate --s3-endpoint https://s3.example.com
```

Для AWS S3 флаг `--s3-endpoint` можно опустить. SDK использует SigV4, path-style
адресацию и проверку TLS по умолчанию. Сетевой клиент работает только на хосте;
контейнер сохраняет `--network=none`, не получает credentials и не обращается к S3.
Образ должен иметь корректную метку `org.opencontainers.image.revision` с полным
Git SHA, иначе публикация/удалённое возобновление отклоняются. Docker image ID
также сохраняется в метаданных.

Лаунчер печатает URI `s3://bucket/prefix/<git_commit>/<run_id>/manifest.json`.
Он периодически отправляет последний атомарно записанный checkpoint и текущие
логи, а после завершения — результаты и окончательные логи. Быстрые промежуточные
поколения могут не попасть в S3: загружается последняя доступная копия, а не очередь
всех поколений. Завершение, защитная остановка, тайм-аут и прерывание различаются
через `status`/`exit_code` в manifest.

Публикуются стандартные файлы `checkpoint.npz`, `result.json`, `console.log`
(объединённые stdout/stderr), `run_evolution.log`, а для гипотез также
`feedback.jsonl`/`prompt.json`. S3-режим использует стандартные имена файлов в
`--output-dir`; переопределять соответствующие пути параметрами Hydra нельзя.
Чужие файлы хоста и символьные ссылки не читаются. Credentials хоста не передаются
в контейнер. Пользовательские данные из разрешённых файлов результата/логов
попадают в выбранный bucket вместе с экспериментом.

Каждый объект имеет размер, SHA-256 и метаданные Git-коммита. Объекты размещаются
по содержимому, а manifest заменяется только после успешной отправки всех файлов.
При сбое загрузки предыдущий manifest остаётся пригодным для восстановления,
локальные файлы сохраняются, лаунчер возвращает ошибку. Промежуточные объекты не
удаляются автоматически; срок хранения задаётся политикой bucket.
Нужны права GetObject/PutObject на свой prefix, а для прерывания multipart-upload —
AbortMultipartUpload. Лаунчер не требует удаления объектов или списка bucket.

Возобновление в новом контейнере:

```sh
python3 run_evolution_docker.py --experiment formulas --resume-s3 s3://my-bucket/aethergate/COMMIT/RUN_ID/manifest.json --output-dir artifacts/formulas-from-s3 --s3-uri s3://my-bucket/aethergate --s3-endpoint https://s3.example.com
```

Замените `COMMIT/RUN_ID` точным URI из предыдущего запуска и повторите прежние
настройки эксперимента. Проверяются Git-коммит образа, схема manifest, принадлежность
объекта запуску, размер и SHA-256 скачанного checkpoint. Затем применяются обычные
проверки совместимости checkpoint с настройками/кодом/окружением. Входной файл
подключается к контейнеру только для чтения; новые файлы пишутся в новую папку и
новый S3 prefix запуска с указанием исходного manifest. `--resume-s3` работает для
`formulas` и `selfplay`; режим гипотез поддерживает публикацию результатов/логов.
Если нужен только импорт без публикации продолжения, не задавайте `--s3-uri`.

Для повторной отправки локально сохранённых файлов и отдельного скачивания есть
команды хоста (Git SHA берите из метки исходного образа):

```sh
python3 experiment_artifacts.py --endpoint https://s3.example.com upload --output-dir artifacts/formulas-s3 --s3-uri s3://my-bucket/aethergate --git-commit FULL_GIT_SHA --experiment formulas --status completed
python3 experiment_artifacts.py --endpoint https://s3.example.com download --manifest s3://my-bucket/aethergate/COMMIT/RUN_ID/manifest.json --git-commit FULL_GIT_SHA --output-file artifacts/downloaded-checkpoint.npz
```

CI использует отдельный сетевой S3-эмулятор Moto 5.2.4 (образ закреплён digest),
тестовые credentials и временный bucket. Для обоих режимов проверяются загрузка
checkpoint/результатов/логов, Git-привязка, SIGKILL, удаление локальной исходной копии,
скачивание из S3 и совпадение продолжения с непрерывным запуском. Отдельные тесты
покрывают отказ загрузки, повреждение объекта, чужой Git-коммит, подмену пути,
символьные ссылки и ошибку записи лога. Реальные credentials и конкретный внешний
провайдер этим CI не проверяются. Совместимость API опирается на стандартный SDK
[boto3](https://docs.aws.amazon.com/boto3/latest/guide/configuration.html);
[Moto](https://docs.getmoto.org/en/latest/docs/server_mode.html) используется только
как тестовый сервис, а не как производственное хранилище.
